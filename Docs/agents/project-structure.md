# Project structure

## Layout

| Path                                              | Responsibility                                                                                                                                  |
|---------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| `Source/aweXpect.Migration.Analyzers`             | Diagnostic descriptors (`Rules.cs`), resources, one analyzer per source library. `netstandard2.0`, not packable on its own.                    |
| `Source/aweXpect.Migration.Analyzers.CodeFixers`  | Code fix providers, one per source library, on top of `AssertionCodeFixProvider`. `netstandard2.0`, not packable on its own.                   |
| `Source/aweXpect.Migration`                       | Packaging project without code: references both projects as analyzers and packs their DLLs into `analyzers/dotnet/cs`.                         |
| `Tests/aweXpect.Migration.Tests`                  | Analyzer and code fix tests, grouped in `FluentAssertions/` and `Xunit/`; Roslyn test verifiers in `Verifiers/`.                               |
| `Tests/aweXpect.Migration.Example.Tests`          | Consumer-style playground that loads the analyzers into a real project. Not run by the pipeline.                                               |
| `Pipeline/`                                       | Fallout build project (see [workflows.md](workflows.md)).                                                                                      |
| `Docs/pages/`                                     | Published user docs: the rewrite tables per source library.                                                                                    |

## Analyzers

- `Rules.cs` declares one `DiagnosticDescriptor` per source library through `CreateDescriptor`, which reads `<id>Title`, `<id>MessageFormat` and `<id>Description` from `Resources.resx`. `Resources.Designer.cs` is generated by `ResXFileCodeGenerator` and checked in; update it together with the `.resx`.
- `FluentAssertionsAnalyzer` reports `aweXpectM002` on every invocation of a method under `global::FluentAssertions` named `Should`. It walks up to the outermost enclosing expression, so the diagnostic covers the whole chain, and skips a `Should()` nested in an argument (for example inside `AllSatisfy(x => x.Should()...)`) so the chain is migrated as one unit.
- `XunitAssertionAnalyzer` reports `aweXpectM003` on every call to `global::Xunit.Assert.*`.
- Both analyzers skip generated code and enable concurrent execution. Method names are compared through `Common/TypeExtensions.GloballyQualifiedNonGeneric`.
- The analyzers report every assertion, whether or not a fix exists. Assertions without a fix keep their warning and are migrated by hand.

## Code fixers

- `AssertionCodeFixProvider` handles registration for all fixers: it fixes the single ID of its rule, uses the batch fix-all provider, accepts invocation, conditional access and lambda nodes, and uses the rule title as the code action title. A fixer that returns the unchanged document offers no fix. `AddUsingIfMissing` inserts a using directive in sorted position when a rewrite needs one.
- `FluentAssertionsCodeFixProvider` collects the subject and the method chain with the nested `ExpressionSyntaxWalker`, then maps the first assertion in `GetNewExpressionFor` (a `switch` on the FluentAssertions method name, with helper methods for the complex cases). `.And` chains are kept, a `because` argument becomes a trailing `.Because(...)`, an assertion that is the body of a lambda is wrapped in `aweXpect.Synchronous.Synchronously.Verify(...)`, and `using aweXpect.Equivalency;` is added for `IgnoringCollectionOrder()`. A chain that continues on a second `Should()` is not fixed.
- `XunitAssertionCodeFixProvider` maps `Assert.<Method>` in `GetNewExpression` (a `switch` on the method name), swapping xUnit's `expected, actual` order to aweXpect's actual-first form. It adds `using System;` when the rewrite uses `Math.Round`.
- The fixers produce `Expect.That(...)` without `await`. Adding `await` and `async` is left to the `aweXpect0001` analyzer and fix in the aweXpect package (see the README).

## Tests

- `CSharpAnalyzerVerifier<TAnalyzer>` and `CSharpCodeFixVerifier<TAnalyzer, TCodeFix>` wrap `Microsoft.CodeAnalysis.Testing`. They compile the test code against .NET 10 reference assemblies, the `xunit.v3` and `FluentAssertions` packages, and the aweXpect assemblies of the test project. `VerifyLegacyCodeFixAsync` uses FluentAssertions 7.2.0 instead of 8.2.0.
- Code fix tests are TUnit tests with a `[MethodDataSource]` over `TestCases.cs` in each folder. Each case is a tuple `(original assertion, expected rewrite, arrange, isAsync)`; the test embeds it in a test method and checks the fix. `AddWithBecause` (FluentAssertions) turns a `{0}` placeholder into one case without and one with a `"because foo"` argument.
- Edge cases that need a full source file (usings, theories, nullable access, cases without a fix) are separate `[Test]` methods in the same class.

## Adding a rewrite to an existing rule

1. Add a branch to the method-name `switch` in `FluentAssertionsCodeFixProvider.GetNewExpressionFor` or `XunitAssertionCodeFixProvider.GetNewExpression`. Return `null` whenever the call cannot be translated without losing an argument or changing behaviour unnoticed.
2. Add cases to the matching category in `TestCases.cs`, including the `because` variant for FluentAssertions. Add overloads that must stay unfixed to `TestCases.NoCodeFix` or a `..._ShouldNotOfferCodeFix` test.
3. Add a row to the table in `Docs/pages/01-fluentassertions.md` or `Docs/pages/02-xunit.md`. If the aweXpect expectation behaves differently in some cases, link the row to a new entry under "Behavioural differences".
4. Run `dotnet test --project Tests/aweXpect.Migration.Tests`.

## Adding a rule for a new source library

1. Declare a descriptor in `Rules.cs` with the next free ID (`aweXpectM004`; `aweXpectM001` was never used), add its three resources to `Resources.resx` and `Resources.Designer.cs`, and list it in `AnalyzerReleases.Unshipped.md`.
2. Add a `DiagnosticAnalyzer` in `Source/aweXpect.Migration.Analyzers` that follows the existing analyzers: `[DiagnosticAnalyzer(LanguageNames.CSharp)]`, generated code excluded, concurrent execution, an operation action on `OperationKind.Invocation`.
3. Add a fixer in `Source/aweXpect.Migration.Analyzers.CodeFixers` that derives from `AssertionCodeFixProvider` with `[ExportCodeFixProvider(LanguageNames.CSharp, Name = nameof(...))]` and `[Shared]`.
4. Add the library package to the `ReferenceAssemblies` in `Tests/aweXpect.Migration.Tests/Verifiers/` and create a test folder with analyzer tests, code fix tests and `TestCases.cs`.
5. Add a page under `Docs/pages/`, then add the diagnostic to the README table, the `dotnet format` command and the "Supported assertions" list.
